# TASK.md — Cryscade

Каскадный слот на кристаллах: кластерные выплаты, точки множителей, фриспины. Портфельный проект под вакансии разработчика клиента слотов: PixiJS, TypeScript, машина состояний, интеграция с сервером, поведение из конфигурации, тесты, мобильная производительность.

**Только игровые кредиты.** Никаких реальных денег, платежей, депозитов, регистрации и ссылок на казино. Баланс пополняется кнопкой. Это витрина инженерии, а не азартная игра.

Файл читается в начале каждой фазы — нужные разделы, не целиком каждый раз. Постоянные правила — в `CLAUDE.md`.

## 1. Что должен увидеть ревьюер

Шесть свойств, ради которых проект существует. Каждое доказывается тестом или замером, а не словами README.

1. **Сервер решает, клиент показывает.** Сервер игры (RGS) работает в Web Worker и говорит с клиентом по версионированному протоколу. Клиентский код не импортирует генератор исходов — это проверяет тест графа импортов.
2. **RTP ровно 96.00%.** Исход выбирается по весам из заранее построенной книги раундов — так устроены современные открытые RGS. RTP считается по книге в целых числах и сверяется тестом с точностью 1e-9, а не оценивается симуляцией.
3. **Проверяемая честность.** Выбор исхода — HMAC-SHA256 от секрета сервера (с заранее опубликованным хешем), сида игрока и номера раунда. Любой раунд из истории перепроверяется и воспроизводится; `?replay=book:N` открывает раунд в любом браузере.
4. **Кадр — функция событий раунда и времени.** Презентация строится как расписание и читается чистой функцией `sampleScene(schedule, t)`. Отсюда без отдельного кода: пропуск, турбо, пауза, восстановление посреди каскада после перезагрузки, тесты анимации.
5. **Устойчивость.** Идемпотентные ставки, повтор после обрыва без двойного списания, восстановление незавершённого раунда, две вкладки на одном кошельке. Всё провоцируется руками в «Лаборатории сети».
6. **Правила юрисдикции — данными.** Один билд, два пресета: обычный и строгий по модели требований UKGC. Код читает флаги пресета и нигде не сравнивает его имя.

      │                  ▼                                        ▼

      │                  │                                        │
      │                  ▼                                        ▼

Граница — контракт. Держат её четыре вещи: тест графа импортов, тест запрещённых глобалов в `core/`, `no-restricted-imports` в линтере и типы по средам исполнения (§2: `core/` и `protocol/` без DOM, `server/` — WebWorker без DOM).

Тест графа импортов:
- каждое ребро таблицы — литеральными случаями «можно» и «нельзя»;
- замыкание: из `client/`, `render/`, `ui/`, `audio/` не достижим ни один файл `core/engine`, `core/rng`, `server/`. Прямых рёбер мало: движок может прийти в клиент через разрешённого посредника в `core/`;
- обход обязан найти больше нуля файлов в каждом модуле и больше нуля рёбер;
- относительные импорты в `core/`, `protocol/`, `server/` — с `.ts`;
- тесты в Node не тянут Pixi: из замыкания импортов ни одного файла `tests/` не достижим `pixi.js`. Поэтому Pixi живёт только в `render/pixi/`, а раскладка, геометрия символов, пул и часы декора — данные и функции без него.

- «Может импортировать» — белый список: внешний пакет, которого нет в колонке, запрещён. Сверх колонки разрешены `ui/` — `react`, `react-dom` и два пакета шрифтов, `tools/` — `node:*`.
- Файл в `src/` вне модулей таблицы — нарушение, а не слепая зона. Точка входа — `ui/main.tsx`.
- Импорт, цель которого не проверить (`import(выражение)`, `import.meta.glob`), — нарушение.
- `server/worker.ts` — единственный файл сервера, которому разрешены IndexedDB, Web Locks и BroadcastChannel.
- Клиент создаёт воркер через `new URL('../server/worker.ts', import.meta.url)`. Это не импорт, и тест графа обязан отличать одно от другого.
- Тип событий раунда живёт в `core/model/events.ts`: его видят все, генератор — никто, кроме сервера и инструментов.

## 4. Математика игры

### 4.1 Поле и символы

Сетка 7×7, клетки нумеруются по строкам сверху вниз: `cell = row * 7 + col`.

| id | Символ | Силуэт | Ярус |
|---|---|---|---|
| 0 | Кварц | треугольник | L1 |
| 1 | Аметист | квадрат | L2 |
| 2 | Цитрин | пятиугольник | L3 |
| 3 | Изумруд | вытянутый восьмиугольник | L4 |
| 4 | Сапфир | капля | H1 |
| 5 | Рубин | сердце | H2 |
| 6 | Бриллиант | круглая огранка в профиль | H3 |
| 7 | Ядро (скаттер) | сфера с лучами | — |

Силуэты различаются без цвета — это требование доступности, а не украшение (§9, тест силуэтов).

### 4.2 Раунд

1. **Заполнение** сетки из распределения режима — основная игра или фриспины.
2. **Кластеры:** 5+ одинаковых символов, связанных по вертикали и горизонтали. Ядро кластеров не образует.
3. **Выплата кластера** = значение из таблицы × множитель кластера (§4.3).
4. **Каскад:** все выигравшие кластеры взрываются одновременно, символы падают вниз, сверху досыпаются новые из того же распределения. Повтор, пока есть кластеры. Ядра не взрываются и падают вместе с остальными.
5. **Счёт ядер** — в конце цепочки каскадов: 3 / 4 / 5 / 6+ → 10 / 12 / 15 / 20 фриспинов.
6. **Фриспины:** своё распределение символов; 3+ ядра за спин — ещё 5 спинов; точки множителей живут до конца фичи.
7. **Кап:** 5000× ставки за раунд, основная игра вместе с фичей. Проверяется после каждого шага выигрыша — всех кластеров шага разом. Шаг, на котором сумма раунда дошла до капа, обрезается ровно до 5000×; его кластеры подсвечиваются, но не взрываются. После капа нет ни взрыва, ни точек, ни досыпки, ни счёта ядер, ни одного запроса к источнику символов; итоговая сетка полная. Оставшиеся фриспины сгорают; кап в основном спине не открывает фичу, сколько бы ядер ни лежало на сетке.

Раунд — это спин основной игры и вся фича, которую он открыл. Одна ставка, один итог.

### 4.3 Точки множителей

Каждая клетка, где взорвался символ, получает отметку. Повторный взрыв в отмеченной клетке делает её множителем ×2, каждый следующий удваивает его, максимум ×128. Множитель кластера — сумма множителей его клеток; если таких клеток нет — ×1. Множитель считается по уровням **до** взрыва, потом уровни обновляются. В основной игре точки сбрасываются в начале каждого спина, во фриспинах живут до конца фичи. Фриспины начинаются с чистого поля: отметки и множители основного спина в фичу не переходят.

Механика — жанровый стандарт кластерных слотов. Название, арт, цифры и код — свои.

### 4.4 Таблица выплат

Множители от общей ставки. ### 4.6 Деньги

- Все суммы — целые минимальные единицы, сотые кредита. Ни одного float в балансе и выплатах.
- Выплаты хранятся в сотых долях ставки (`payX100`) — тоже целыми.
- Ставки: 0.20, 0.40, 1, 2, 4, 10, 20, 50, 100 кредитов. Стартовый баланс 1000, кнопка «Пополнить» возвращает 1000.
- Выигрыш раунда = `floor(bet × payX100 / 100)`: одно округление в конце раунда, вниз. Закреплено тестом с литералами.

### 4.7 ГСЧ и движок

- `core/rng`: xoshiro128**, состояние из 32-битного сида через splitmix32. У каждого раунда свой сид; поток раунда не зависит от соседних.
- `core` крипто не трогает. Криптостойкие сиды — забота сервера.
- Сетка — `Uint8Array(49)`, точки — `Uint8Array(49)`: 0 — нет, 1 — отметка, k от 2 до 8 — множитель ×2^(k−1). Поиск кластеров — заливка с предвыделенным стеком, без аллокаций в цикле.
- Два режима одним кодом: тихий (только итог — для симуляции) и записывающий (события — для сервера и повторов). Разница только в рекордере. Тест: на 10 000 сидов оба режима дают один итог.
- Поток символов раунда — часть определения игры: от него зависят книга и повтор, изменение — пересборка книги.
  - splitmix32: шаг Вейля `state += 0x9E3779B9`, выход — `fmix32` из MurmurHash3 (сдвиги 16, 13, 16; множители `0x85EBCA6B`, `0xC2B2AE35`).
  - Состояние xoshiro128** 1.1 — первые четыре выхода splitmix32 от сида раунда, по порядку `s[0]…s[3]`. Все четыре нулями быть не могут: `fmix32` — биекция, ноль она даёт только на нуле.
  - Символ — `u32` из xoshiro128**. Значение не меньше `2³² − (2³² mod W)`, где W — сумма весов режима, отбрасывается и берётся следующее; иначе `u32 mod W` ищется по накопленным весам в порядке id.
  - Заполнение спрашивает клетки 0…48 по порядку, досыпка — пустые клетки по возрастанию номера.
- Сторож: `SeededEngine({ maxRequests })` — порог запросов к источнику за раунд. Порог задаёт вызывающий, у движка своего нет. Срабатывание — всегда ошибка `WatchdogError` с сидом, никогда не пропуск сида: пропуск молча сместил бы статистику и книгу. Обоснование порога — самый длинный честный раунд на конфиге вызывающего, с запасом:
  - тесты — 100 000: самый длинный на 10⁵ сидах — 2017 у стресс-конфига, 1072 у черновика игры;
  - симулятор — 1 000 000: самый длинный раунд итогового конфига игры на 10⁸ сидах — 2166 (сид 47564878), черновика — 1893; порог в сотни раз выше, чтобы кандидаты подбора с длинной фичей проходили, а надкритичный падал, а не висел.
- Детерминизм между движками JS. Книгу строит V8, а повтор по ссылке может пересчитать Safari; `log`, `exp`, `pow` и оператор `**` спецификация разрешает считать приближённо — последний бит вправе разойтись. Поэтому в `core/engine`, `core/rng` и `core/money.ts` из `Math` — только `imul`, `clz32`, `min`, `max`, `abs`, `floor`, `trunc`, а `**` нет. `+ − × /` и `%` по IEEE 754 округляются однозначно и разрешены. Держит правило линтера `cryscade/deterministic-math`.

### 4.8 События раунда

```ts
// core/model/events.ts — в коде все поля readonly
type WinCluster = { symbol: number; cells: number[]; payX100: number; mult: number };
type RoundEvent =
  | { t: 'fill'; grid: number[] }
  | { t: 'win'; clusters: WinCluster[] }
  | { t: 'explode'; cells: number[] }
  | { t: 'spots'; cells: number[]; levels: number[] }
  | { t: 'refill'; moves: [from: number, to: number][]; drops: { cell: number; symbol: number }[] }
  | { t: 'scatters'; cells: number[] }
  | { t: 'fsStart'; spins: number }
  | { t: 'fsSpin'; index: number; left: number }
  | { t: 'fsRetrigger'; add: number }
  | { t: 'cap' }
  | { t: 'end'; payX100: number };
```

Требование одно: события описывают раунд полностью, по ним одним презентация восстанавливает любой момент. Формат закреплён в фазе 1:

- `fill` — 49 символов нового спина.
- `win` — кластеры шага по наименьшей клетке, клетки кластера по возрастанию. `mult` — сумма множителей клеток кластера по уровням до взрыва, 1 — если их нет. `payX100` — **после** множителя: `таблица × mult`, в тех же единицах, что `end`; табличное значение — `payX100 / mult`, делится нацело.
- `explode` — объединение клеток кластеров предыдущего `win`, по возрастанию. На шаге капа его нет — поэтому он отдельное событие.
- `spots` — клетки, чей уровень изменился, и их новые уровни в кодировке §4.7 (1 — отметка, k — ×2^(k−1)). Идёт после каждого `explode`; пуст, если все клетки уже ×128.
- `refill` — `moves` только для сдвинувшихся символов, по колонкам слева направо, в колонке снизу вверх; `drops` — по возрастанию клетки.
- `scatters` — ядра на сетке по возрастанию; пишется, когда ядра дают фриспины по конфигу (для конфига игры — от трёх), следом `fsStart` или `fsRetrigger`.
- `fsStart` — фича началась, поле точек чистое.
- `fsSpin` — `index` с 1; `left` — сколько спинов останется после этого, без будущих ретриггеров.
- `cap` — сразу после `win`, на котором сумма раунда дошла до капа; следом `end`.
- `end` — `payX100 = min(кап, Σ payX100 всех кластеров всех win)`.

Грамматика:

```
раунд = спин [ scatters fsStart { fsSpin спин [ scatters fsRetrigger ] } ] end
спин  = fill { win explode spots refill }
кап обрывает раунд: win, на котором сумма дошла до капа, идёт как  win cap end
```

## 5. Книга исходов и точный RTP

**Почему.** Высокая волатильность делает Монте-Карло грубым: при σ порядка 15 ставок на раунд 10⁷ симуляций дают 99%-интервал RTP около ±1.2 процентного пункта. Современные открытые RGS решают это иначе: исходы посчитаны заранее, у каждого вес, сервер выбирает раунд с вероятностью, пропорциональной весу. RTP игры тогда — точная сумма по таблице.

**Построение** (`tools/books`):

1. Симуляция 10⁸ раундов на фиксированном диапазоне сидов [0, 10⁸) — тот же диапазон, что у итогового отчёта фазы 2: его прогноз сверяется с книгой. Подбор весов в фазе 2 идёт на других сидах, от 2³¹.
2. Корзины по выплате, в ставках: 0; (0, 1]; (1, 2); [2, 5); [5, 10); [10, 20); [20, 50); [50, 100); [100, 250); [250, 500); [500, 1000); [1000, 2500); [2500, 5000); 5000. Граница по 1× точная: выигрыш ровно в ставку попадает в (0, 1], поэтому доля «больше ставки» — празднование строгого пресета — считается по корзинам точно.
3. Из каждой корзины сохраняется до K раундов, редкие — все. Вес раунда — доля его корзины в симуляции, делённая на число сохранённых, приведённая к целым.
4. Пул проигрышных раундов получает суммарный вес, при котором RTP книги равен 0.96. Суммы — в `BigInt`; отклонение от 0.96 меньше 1e-9 закреплено тестом.
5. Все показатели отчёта — частота выигрыша, фичи, распределение, σ, частота максимального выигрыша — пересчитываются по книге, точно.

Про хвост честно: если симуляция нашла мало раундов в верхних корзинах, отчёт так и пишет, с числами.

**Формат.** Двоичный, little-endian: заголовок (`CRYB`, версия u16, число записей u32, сумма весов u64), затем записи `seed u32, payX100 u32, weight u32`. Сжат gzip в `public/books/base.v1.bin.gz`, рядом манифест с SHA-256 и статистикой. Не больше 80 000 записей и 1 МБ в сжатом виде. Чтение и запись формата — один модуль в `server/`, его используют и генератор, и воркер.

**Загрузка.** Воркер тянет книгу лениво, после первого кадра игры, распаковывает `DecompressionStream('gzip')`, сверяет SHA-256 через `crypto.subtle.digest` и читает `DataView`. Не сошлось — ошибка, а не игра на битых данных.

**Раунд из книги — это сид.** Сервер выбирает запись, движок восстанавливает события из её сида. Книга хранит итог и вес, а не события.

## 6. Протокол и сервер

### 6.1 Сообщения

Каждое сообщение — конверт `{ v: 1, id, body }`; `id` связывает запрос с ответом. Несовпадение `v` — ошибка `VERSION_MISMATCH`.

| Запрос | Ответ |
|---|---|
| `authenticate` | баланс, конфиг (ставки, пресет, кап), активный раунд или `null`, обязательство честности (с фазы 6) |
| `play { betMinor, idempotencyKey }` | раунд: `roundId`, ставка, выигрыш, события, индекс книги, `nonce`; баланс после списания |
| `endRound { roundId }` | баланс после зачисления; повторный вызов возвращает тот же ответ |
| `setClientSeed { clientSeed }` | новое обязательство |
| `rotateSeed` | раскрытый секрет и новое обязательство |
| `history { limit }` | последние раунды |
| `replay { round: id } \| { book: index }` | события раунда без движения денег |
| `resetBalance` | баланс 1000 |

Ошибки — размеченное объединение: `INSUFFICIENT_FUNDS`, `ROUND_ACTIVE`, `ROUND_NOT_FOUND`, `INVALID_BET`, `IDEMPOTENCY_CONFLICT`, `BAD_REQUEST`, `VERSION_MISMATCH`, `INTERNAL`.

Каждое входящее сообщение проверяется на границе написанными вручную гардами. Property-тест: на произвольном мусоре гард не бросает и возвращает `false`.

### 6.2 Правила сервера

- Один активный раунд на кошелёк. `play` при активном раунде — `ROUND_ACTIVE`: клиент обязан сначала восстановиться.
- `play` списывает ставку и записывает активный раунд атомарно; `endRound` зачисляет выигрыш и закрывает раунд.
- Идемпотентность: ключ → `roundId`. Повтор с тем же ключом возвращает сохранённый раунд без нового списания; тот же ключ с другим телом — `IDEMPOTENCY_CONFLICT`.
- Сначала запись, потом ответ. Потерянный ответ не теряет раунд.
- Хранится: кошелёк, последние 100 раундов, ключи идемпотентности, текущий секрет и раскрытые прошлые, `nonce`.

### 6.3 Две вкладки и IndexedDB

- Все изменения кошелька — под эксклюзивной блокировкой Web Locks `cryscade-wallet`: у всех вкладок один писатель.
- Внутри транзакции IndexedDB нельзя ждать ничего, кроме запросов самой IndexedDB: транзакция закроется на первом `await crypto.subtle`. Порядок: блокировка → чтение → криптография и движок → одна короткая транзакция на запись.
- BroadcastChannel сообщает остальным вкладкам о смене баланса и активного раунда.

### 6.4 Порты

Логика сервера зависит от портов `Storage`, `Lock`, `Clock`, `Entropy`, а не от браузера. В юнит-тестах — адаптеры в памяти; настоящие — IndexedDB, Web Locks, `crypto.getRandomValues` — только в `worker.ts` и проверяются e2e.

### 6.5 Клиент

- `RgsClient` не знает транспорта. По умолчанию — воркер; обёртка «Лаборатории сети» добавляет задержку, разброс, потерю запроса, потерю ответа и таймаут.
- Повтор с тем же ключом идемпотентности через 250, 500, 1000, 2000 мс, дальше экран ошибки с кнопкой «Повторить».
- Разовые действия лаборатории: «потерять следующий ответ», «перезагрузить страницу посреди следующего раунда».
- Восстановление: `authenticate` вернул активный раунд → презентация прыгает к контрольной точке из `sessionStorage` (`roundId → t`), доигрывает и вызывает `endRound`. Точки нет — с начала раунда.

## 7. Честность

- Секрет сервера — 32 случайных байта; обязательство — SHA-256 секрета в hex, показано до игры.
- Сид игрока редактируется, по умолчанию 16 случайных hex-символов. `nonce` растёт с нуля.
- Выбор исхода: `HMAC-SHA256(key = секрет, msg = "${clientSeed}:${nonce}:${counter}")`, первые 8 байт — `uint64` big-endian. Значения ≥ `floor(2⁶⁴ / W) · W`, где W — сумма весов, отбрасываются (`counter + 1`), иначе остаток от деления на W. Бинарный поиск по накопленным весам даёт индекс книги, движок восстанавливает события из сида записи.
- Смена секрета раскрывает старый и публикует новое обязательство; `nonce` с нуля.
- Панель «Проверить»: секрет, сид, `nonce` → пересчёт → совпадение с историей.
- История — последние 100 раундов: время, ставка, выигрыш, индекс книги, `nonce`, обязательство; «Проверить» после раскрытия и «Воспроизвести».
- Повтор: `?replay=round:<id>` из своей истории и `?replay=book:<index>` в любом браузере. Плашка «Повтор», деньги не двигаются, спин выключен. В README — ссылка на повтор максимального выигрыша из книги.
- README говорит прямо: сервер в браузере — демонстрация, секрет лежит на устройстве. Протокол тот же, что у удалённого сервера, транспорт меняется одним адаптером.

Тесты: HMAC сверяется с независимой реализацией `node:crypto` на фиксированных входах; отбрасывание проверяется подставным источником байтов — значение за границей обязано уйти на следующий `counter`.

## 8. Клиент: машина состояний и презентация

### 8.1 Машина состояний

Паттерн State: состояние — объект, переход — чистый метод `on(event) → { state, commands }`. Команды — данные (`CallPlay`, `CallEndRound`, `StartPresentation`, `ShowError` и т. п.), исполняет их контроллер. Состояния: `booting`, `authenticating`, `idle`, `requesting`, `presenting`, `featureIntro`, `ending`, `restoring`, `replaying`, `error`. Полнота — через `never` в `switch` по событию. Табличный тест покрывает каждую пару (состояние, событие); недопустимая пара возвращает то же состояние с пометкой `ignored` и не бросает.

### 8.2 Расписание

- `buildSchedule(round, speed, preset)` → сегменты с началом и концом во времени.
- `sampleScene(schedule, tMs, out)` пишет в предвыделенный `SceneState`: позиция, масштаб, альфа, поворот, символ и слой каждой клетки и падающих символов; счётчик выигрыша; подсветки; точки множителей; плашки фичи. Ноль аллокаций на кадр.
- Пропуск: первый тап — к концу текущей группы сегментов, второй — к концу раунда. Уход вкладки — часы презентации стоят. Восстановление — прыжок к контрольной точке.

### 8.3 Тайминги

Параметры ощущения, одним блоком констант, правятся на глаз. Миллисекунды.

| Сегмент | обычный | турбо | строгий |
|---|---|---|---|
| сброс старой сетки | 220 | 120 | 220 |
| задержка между колонками при падении | 45 | 20 | 45 |
| подсветка кластера | 450 | 200 | 450 |
| взрыв | 260 | 160 | 260 |
| обновление точек множителей | 280 | 150 | 280 |
| счётчик выигрыша | 300–2000 по логарифму выигрыша | ×0.5 | как обычный |
| минимальный цикл спина | 0 | 0 | 2500 |

Падение аналитическое: ускорение, касание ровно в целевой клетке в расчётный момент, короткий отскок с затуханием. Никаких подобранных на глаз твинов.

### 8.4 Выигрыши

- Контур кластера — marching squares по маске клеток: многоугольник, с дырами, если они есть, а не рамки вокруг клеток.
- Уровни большого выигрыша: «Крупный» от 20×, «Огромный» от 50×, «Эпический» от 100×, «Максимум» на 5000×. Всё пропускается.
- Вспышки и пульсации — не чаще 3 в секунду (WCAG 2.3.1), проверяется по расписанию.
- `prefers-reduced-motion`: падения короче и без отскока, частиц и тряски нет, фон статичен.

### 8.5 Тесты презентации

- Литералы на фикстурах: конец расписания даёт ровно итоговую сетку раунда.
- Property: в конце каждой группы сегментов каждая клетка занята ровно одним символом в покое; счётчик выигрыша монотонен и заканчивается итогом; `sampleScene` в момент t не зависит от предыдущих вызовов.
- Контур замкнут и содержит центры ровно клеток кластера.
- Строгий пресет: при выигрыше ≤ ставки нет празднующих сегментов; цикл не короче 2500 мс.

**Огранка — процедурно.**
1. Силуэт — многоугольник; площадка — внутренний многоугольник в 0.45–0.55 от внешнего, чуть выше центра.
2. Грани — четырёхугольники между ребром силуэта и ребром площадки, плюс сама площадка.
3. У каждой грани фиктивная нормаль с наклоном наружу. Свет: ключевой сверху слева, заполняющий, бирюзовый контровой снизу. Плоская заливка по Ламберту и лёгкий градиент вдоль грани.
4. Блик-звезда на верхних гранях, тонкая светлая кромка сверху, тёмная обводка 1.5 единицы — отделяет кристалл от любого фона.
5. Всё рендерится один раз в 2× в общий атлас: символы, свечение (размытый силуэт для подсветки), осколки для частиц. Одна базовая текстура — один батч.

**Рамка** — огранённый край с медленным бликом.

**Фон** — один полноэкранный шейдер: градиент грота, каустики, медленная пыль. Пара GLSL и WGSL. При reduced motion время шейдера стоит.

**Фриспины** — грот теплеет, рамка ярче, точки множителей заметно «заперты».

**Шрифты.** Unbounded — числа и заголовки, Manrope — интерфейс. Счётчики в Pixi — BitmapFont из Unbounded, установленный только после `document.fonts.load`.

## 10. Рендер на Pixi

- `await app.init({ preference: 'webgpu', ... })` с откатом на WebGL. WebGPU с января 2026 входит в Baseline (Chrome, Edge, Firefox на Windows и macOS, Safari 26), но есть не везде — откат обязателен. `?renderer=webgl|webgpu` работает и в проде: нужен для проверки на телефоне. В CI WebGPU обычно нет — это заодно проверка отката.
- В 8.21 появились `ExtensionType.WebGLLoader`, `WebGPULoader`, `CanvasLoader` для ленивой загрузки бэкендов. Использовать, только если замер покажет уменьшение начального чанка: мерить до и после. Фаза 3: своих систем и пайпов под один бэкенд у игры нет — загрузчикам нечего переносить; начальный JS e2e-сборки — 247 КБ gzip при обоих рендерерах (бюджет §13 — 300).
- Выигравшие символы — в `RenderLayer` над рамкой: трансформации остаются у сетки, порядок отрисовки — у слоя. Объект, снова добавленный к родителю, к слою сам не возвращается — прикреплять заново.
- Частицы — `ParticleContainer` с текстурами из общего атласа: все частицы контейнера обязаны делить базовую текстуру.
- Счётчики — BitmapText; прокрутка цифр — посимвольно (SplitBitmapText или свой разбор — сверить со скиллами).
- Одновременно не больше двух фильтров. Свой шейдер — только фон; подсветки — аддитивные спрайты, не фильтры.
- Шейдеры прогреваются при загрузке: одна отрисовка каждого конвейера во внеэкранную текстуру 1×1 до первого кадра, без следа на экране. Текстура прогрева — в формате и с MSAA канваса: в WebGPU Pixi кэширует конвейеры отдельно на состояние прохода (формат цвета, MSAA, трафарет), и прогрев в `rgba8unorm` не прогреет конвейер канваса `bgra8unorm`.
- StrictMode монтирует дважды, а `init` асинхронный: монтирования идут цепочкой через промис в рефе; размонтировались во время `await` — приложение уничтожается сразу. React владеет хост-элементом, канвас — поколением рендерера: `PixiRenderer` создаёт его сам и уничтожает с `removeView: true`. Причина (проба на Pixi 8.21, Chrome 153): WebGL-`destroy` вызывает `loseContext()`, и повторный `init` на том же канвасе вешает главный поток страницы; WebGPU пересоздаётся на том же канвасе чисто. Прежняя редакция — «`removeView: false`, канвасом владеет React» — под StrictMode и HMR на WebGL замораживала бы страницу.

**Известные грабли v8**
- `generateTexture` обрезает по границам содержимого — задавать `frame` явно; разрешение задавать явно, по умолчанию берётся DPR устройства.
- `ParticleContainer` с частицами в конструкторе требует одного `update()` после создания, иначе буфер не строится; `boundsArea` обязателен.
- `TilingSprite`: конвейер ставит `repeat`, если геттер `addressMode` не `repeat`. Для зажима по вертикали — `addressModeV = 'clamp-to-edge'` на `style`.
- Уничтожение текстуры, привязанной к общему шейдеру частиц, даёт предупреждение. `warn()` работает и в проде и замолкает после 500 сообщений. Текстуры частиц — кэш рендерера, уничтожается после `app.destroy`.
- Маска и фильтры — на разных контейнерах.
- `cacheAsTexture` под фильтром родителя запекает результат — снимать и ставить заново при смене вида.
- `managedTextures` содержит пустые записи — считать непустые.
- У Pixi два тикера: при замере времени кадра не смешивать их кадры.
- WebGL-`destroy` теряет контекст канваса (`loseContext`): новый рендерер — только на новом канвасе.
- Группы привязок батча WebGPU (`getTextureBatchBindGroup`) — модульный кэш, `releaseGlobalResources` его не чистит: уничтожение источника текстуры, побывавшей в батче, даёт предупреждение и после `app.destroy`. Источник атласа не уничтожать — его GPU-память уходит с рендерером.
- Батч рвётся на `maxBatchableTextures` (16) разных текстурах, а не на первой новой: контроль счётчика draw-call — больше 16 разных текстур.
- Маска-прямоугольник — трафарет с лишними draw-call: `ScissorMask` в 8.21 есть, но его конвейер не зарегистрирован. Край сетки при падении — альфой по высоте.
- Временные ресурсы на выпечке — `FillGradient`, `BlurFilter` — остаются в группах привязок: их уничтожение или `releaseGlobalResources` дают «destroyed while still bound» при перемонтировании. Атлас выпекается без них: градиенты — полосами и стопками кругов, свечение — стопкой расширенных силуэтов.

## 11. Оболочка на React

- Состояние контроллера — через `useSyncExternalStore` с селекторами. Счётчик выигрыша крутится в Pixi, не в React. Бюджет — не больше 10 рендеров App за раунд без ввода, замерить.
- Панель: спин, ставка ± и выбор ставки (Popover API), турбо, автоигра, баланс, выигрыш, меню.
- Диалоги — нативный `<dialog>`: правила и выплаты, настройки, история, проверка честности, лаборатория сети.
- **Правила и выплаты строятся из данных модели.** Тест сверяет отрисованные значения с литералами.
- Автоигра: 10 / 25 / 50 / 100 спинов; остановки — на фиче, на выигрыше от N×, на потере от L; остановка на любой ошибке.
- i18n: украинский по умолчанию и английский; словари с одинаковым набором ключей — тест; суммы через `Intl.NumberFormat`.
- Доступность: вся игра с клавиатуры (пробел — спин, ± — ставка, Esc — закрыть), видимый фокус, объявления выигрыша через `aria-live`, контраст AA.
- Раскладка панели — container queries и отступы безопасной зоны.
- Оверлеи поверх живой сцены пропускают тап на канвас (`pointer-events: none`, интерактивным детям — `auto`). Оверлеи над замершей сценой тап перехватывают.

## 13. Бюджеты и замеры

| Что | Бюджет |
|---|---|
| draw-call (WebGL): покой / каскад / большой выигрыш | ≤ 15 / ≤ 25 / ≤ 35 |
| начальный JS без книги | ≤ 300 КБ gzip |
| книга | ≤ 1 МБ gzip, загружается лениво |
| атлас | ≤ 2048×2048 |
| аллокации в `sampleScene` | 0 |
| память за 300 спинов | куча после сборки ≤ +5% к отметке 50-го спина; живых текстур не прибавляется |
| кадр | без подёргиваний на телефоне — финальная проверка за мной |

Правила замеров:
- Инструменту верят после того, как он поймал положительный контроль.
- Синтетический ввод — чтобы привести игру в состояние. Когда предмет замера — путь ввода, только клик по координате с настоящим попаданием по слоям.
- Производительность только на GPU: печатать строку рендерера, на SwiftShader отказываться считать. Локально — системный Chrome с `--use-angle=metal`.
- Худшее из N прогонов, не лучшее.
- Время кадра — изнутри кадра, а не по частоте rAF окружения.
- Разметка фаз кадра для DevTools (`performance.measure` с `detail.devtools`) — только в dev. Отсутствие в прод-бандле проверяется грепом с положительным контролем.
